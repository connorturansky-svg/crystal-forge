# WT-024 — Universal contextual help: implementation blueprint

> **Status (23 November 2026): owner-approved product direction, research/planning only. Not implemented or released.** Canonical issue: [#152](https://github.com/connorturansky-svg/crystal-forge/issues/152). Baseline main at audit: `d2ee1ab84ea41d363d9448df436732a286bf2c54`. Always fetch live main, issues and active PRs; this SHA is not a standing branch pointer.

## Decision in one minute

Replace the single top-bar **ⓘ Descriptions** action and the persistent right-column `#contextHelp` card with **two independent, compact, labelled checkbox-style preferences**:
- **Hover notes** — a concise explanation appears when a setting is hovered/focused. On touch, provide a small explicit help control or equally discoverable click target.
- **Detailed explanations** — an accessible, distinctly styled, **in-flow explanation immediately adjacent to the setting itself**, wherever that setting exists. Not a separate card in the right sidebar.

Preferences are global **view settings**, not per-model design settings. Both on, either on, or both off must work; switching workspace, model family, light/dark, Simple/Advanced, project, or modal cannot silently change them. Keep user value, focus, search/navigation and edit history intact.

**Interpretation:** These are two global tick boxes replacing the old Description button, not two tick boxes to append beside every parameter. Individual settings get context help affordances and inline content under the chosen global modes.

## Research and actual source audit

Current `tooltips.js` has `SETTINGS` (113 keys), `BUTTONS` (36 keys), `describeControl(el)` and one installed singleton tooltip. Its lookup is based on `data-state`, element ID, a handful of navigational `data-*` attributes and native `title`. It does **not** inherently resolve dynamic `data-model-param` values or the many runtime data fields generated by the unified Studio.

`studio-v3.js` installs tooltips and, separately at initialization, manages a legacy `crystal-forge-descriptions` localStorage key and updates `#contextHelpTitle` / `#contextHelpBody` on pointerover, focusin and change. That explains why current long-lived descriptions only appear on the right. Both systems repeat the same short text; the long tier does not yet exist.

`index.html` defines 112 distinct classic `data-state` values; **15 were missing exact keys** from `tooltips.js` at this snapshot. See [source-level coverage audit](WT024_HELP_COVERAGE_AUDIT.md). It also owns the top-bar button, hard-coded tooltip styles and old Help entry for PR4. `sensory-studio.js` builds seven native family control groups in `control(schema,p)` using `data-model-param` and dynamically regenerates pixel, mount, wiring, print and modal controls. `studio-catalogue.js` contains at least 69 distinct literal native parameter keys. No claim that counting keys proves complete UI coverage.

The existing `.control-tooltip` uses `pointer-events:none`; this needs revision for hoverable popup content. Previous tooltip and keyboard improvements already exist; **reuse and extend**, do not remove Escape, focus handling, descriptor merging, or view edge positioning. Existing `.control-help` and warning/status text must not be duplicated or hidden when long help is on.

**Architecture:** plain ESM, no framework, GitHub Pages served from `index.html`. `tooltips.js` is the established shared owner. `sensory-studio.js` is the runtime generator. Search is `studio-tool-registry.js` → `studio-tool-search-core.js` → `studio-tool-finder.js`; retain their focus and workspace-routing invariants. Do not edit `app.js` (old demo), change geometry, add remote services, or introduce a second settings store.

## UI and semantics contract

### Global control
At the existing Descriptions top-bar location show two clearly distinguished compact controls:

```text
[✓] Hover notes      [ ] Detailed explanations
```

Use native checkboxes or equivalent fully accessible checked-state controls, visible labels, keyboard toggle via Space, and touch-sized targets. Avoid a disclosure button with unknown state. On narrow screens wrap or expose an accessible small Help preferences group **without losing direct discoverability**. Do not steal the global Search box or push critical Print/Save actions off-screen. The two checkboxes must not be focus traps.

Default on a fresh install: **Hover on; Detailed off.** Legacy `crystal-forge-descriptions=on` migrates to **Detailed on**; Hover stays on by default. For legacy off or no key, default Detailed off. After first successful new preference write, the new versioned preference key is authoritative. If storage is blocked or corrupt, continue in-memory with safe defaults, do not crash or touch project state. Keep the old key read-only for migration and do not delete other users' settings as part of a help change. Suggested key: `crystal-forge-help-preferences-v1`, with `{hover:true,inline:false}` plus a version; validate types on read.

**Do not add either preference to `state.project`, model parameters, project vault, JSON backup, print jobs or manufacturing fingerprints.** No setting change/dirty indicator/mesh invalidation from merely showing or dismissing help.

### Short tooltip
- One useful plain-language sentence (usually 10–25 words), scoped to the actual setting. Readable without knowing CAD terms.
- Keyboard focus and pointer hover; Escape dismisses *only help*, not current edit. Do not open from incidental change events if hover preference is off.
- Popup uses `role=tooltip`, preserving existing `aria-describedby` IDs (especially errors). When it appears, append its ID once; remove only that ID when hidden. Never replace the accessible name/label.
- Stay open while pointer moves from trigger to tooltip; dismiss when leaving both or on Escape. No links/focusable children within a tooltip. Use a disclosure/dialog if later content needs interaction.
- Reposition/clamp in viewport, handle zoom, scrolling and viewport edges. On touch, explicit small trigger must show the summary on click/tap, and allow dismissal.
- If Hover notes is off, no hover/focus popup; existing user-facing safety errors and validation remain.

### Detailed inline help
- Each setting's explanation belongs immediately **after its own labelled control group** in normal document flow, not as a global floating/right-side panel.
- Write a genuine explanation: **What does it change? Why or when would I use it? What might happen to the model or print? What should I check?** Include a practical example when it clarifies a choice.
- Prefer a legible two- or three-sentence paragraph (roughly 35–90 words when necessary). Complex risks may have a short second paragraph; don't produce another technical manual under each slider.
- Distinguish the levels using words ("About this setting", summary text), spacing, typography and separate colour tokens. **Do not rely on colour alone.** Do not use very pale grey/purple text. Test normal text contrast >= 4.5:1 across both themes; preserve selected family theme.
- Keep **warnings/status/errors independent** of these preference switches. Do not show unverifiable "safe" defaults, certification, fixed output power, guaranteed Cura supports or fixed material consumption.
- In-flow text belongs after a label/input or `fieldset`, **not nested into an interactive `label`**. It must not activate inputs when clicked. Reading order and stable IDs should connect it to its control/heading without forcing screen readers to reread 90 words every time a user enters the field. Short hints may be described by `aria-describedby`; long prose should remain navigable separately in document order.

### Dynamic and complete coverage
A single exported help registry (for example `studio-context-help-content.js` or an extension of `tooltips.js`, chosen after inspecting current main) must hold semantic keys and both text levels. Suggested contract:

```js
{
  key: "build.pixelFit",
  label: "LED socket clearance",
  short: "Extra room around the LED so its printed opening can fit your actual part.",
  detail: {
    what: "This adds a clearance allowance to the LED socket opening.",
    use: "Use a measured fit test rather than guessing from the LED's advertised size.",
    effect: "More clearance can ease insertion but may loosen retention.",
    check: "Print a coupon in the intended filament before relying on it."
  }
}
```

This is an **illustrative proposed schema**, not existing source. Agent should keep content as text, not interpolated HTML, and assign stable help IDs from family/section/key/instance, not only a label. Reuse established `describeControl` for legacy paths or adapt it behind a compatibility wrapper. Dynamic value-dependent summaries (e.g. magnet vs screws) should remain accurate after changing a select; missing IDs should fail a coverage test, never be silently counted because a generic title fallback appeared.

Wire up all of:
1. Classic `data-state`, control rows, button actions and advanced/revealed conditionals in `index.html`;
2. Every seven-family `parameterSchema` field through the existing `control(schema,p)` renderer, including shared keys with family-specific meaning;
3. Native `data-` controls created in pixel backing/fittings, mounting patterns, wire routes, print/cura/material controls and modal editors;
4. Header, library/project chooser, contextual centre controls and setup dialogs **where settings/actions exist**, not only `.right`.
5. User-facing statuses that aren't settings should keep their existing warnings without fake help clones.

Prefer instrumentation in the **existing renderers** (plus event delegation) to blind app-wide DOM mutation/observer injection. The UI is rerendered; prevent duplicate help nodes, duplicate listeners, stale model descriptions and focus loss. Content should be lazily materialised for visible controls when Detailed=on, not thousands of hidden extra blocks. Conditional controls receive the same help when they appear.

### Copywriting requirements — human before technical
No "Sets the X parameter" explanations. Start with the user's goal and plain consequence. Technical words may follow in brackets when needed. For every field, review (a) identity and units (b) action/real-world consequence (c) meaningful trade-off (d) related safety/fit limitation (e) example if relevant. The short and detailed tiers must **add information**, not duplicate sentences.

Real examples (authoritative copy still needs family review):

| Setting | Hover note | Detailed inline wording |
|---|---|---|
| Crystal spacing | Moves crystals farther apart or closer together in a regenerated formation. | Increase this if the crystals look crowded or their roots overlap. Extra spacing can make a formation easier to inspect, but also makes the base wider and could exceed your printer bed. After regenerating, check the whole footprint and the real prepared mesh. |
| Edge finishing | Softens selected exposed edges in the actual printed geometry. | Use a small bevel or rounding amount on edges someone is likely to touch. More rounding changes the outline and may take away material near sockets or mounting holes. Check the finished geometry; a software bevel alone cannot prove a print is safe to handle. |
| LED fit clearance | Adds room around the real LED in its printed socket. | A socket cut to the exact advertised LED diameter may print too tight. Increasing clearance can help the LED fit, but too much may leave it loose. Print a small fit coupon with your actual printer and material before choosing an allowance. |
| Radial mounting pattern | Spaces fixing holes evenly around a circle you can move or rotate. | Use this when magnets or screws must sit at equal angles around a point, such as magnets passing a Hall sensor. Changing the circle's centre moves the entire group without changing the spacing between holes. Check that every hole still has enough material around it. |
| Wave amplitude | Makes the wave higher or flatter. | Increase the height of the wave for a more pronounced surface. A bigger wave can change where fittings meet the surface, so inspect any holes and their remaining material before preparing the print. |
| Gear bore | Changes the opening through the centre of a gear. | Choose a bore that suits the shaft or axle you intend to use. A wider hole leaves less material between the bore and nearby spokes or the hub edge. Confirm the actual through-hole in the prepared STL or 3MF and physically check its fit. |
| Dual material | Separates designed regions for printing with more than one material. | Turn this on only when you plan to use compatible multiple material regions. It doesn't automatically produce a working two-colour print or change your physical printer configuration. Review the prepared material bodies and the slicer's machine setup. |
| Prepare print mesh | Creates a manufacturing model, separately from the quick editable preview. | The design preview can show overlapping shapes that are not one printable part. Preparing the print creates the actual joined/cut geometry and checks it for reported problems. You still need to inspect the exported layers in Cura and test physical fit for sockets and mounts. |

**Do not ship the examples as facts until the control's actual code and geometry behaviour have been reviewed.** In particular, do not imply every family has every option. Native-family copy for Tactile Tiles, Control Caps, Characters and Light Pods must be authored and audited in the implementation PR.

## Test and acceptance contract

| Area | Minimum executable evidence |
|---|---|
| Registry | Deterministic coverage manifest for visible classic keys, every family schema key, dynamic specialised selectors; each has useful short + detail or explicit reviewed exception with rationale |
| Preferences | All four combinations; persistence across reload/model/workspace and Simple/Advanced; one-time legacy migration, malformed/denied storage; no project dirty/write or unintended save |
| Classic Crystal | Existing `browser-smoke.mjs` description/tooltip assertions migrated, 15 missing mapped settings covered; mount select content updates correctly |
| Seven builders | Real Chromium visits all family-specific Design/Build/Pixels/Wiring/Mounting/Print Centre paths (plus Home and Library where relevant), shows inline help physically attached to rendered control, changes a value and observes no loss of edit state after rerender |
| Accessibility | Mouse hover→popup crossing, focus, Escape, touch trigger, light/dark contrast, keyboard tab order, mobile 390 px and text zoom, existing error descriptions preserved; no focus trap |
| Layout | Side/centre/header/dialog locations; no hidden right sidebar dependency, no overlay blocking sliders, predictable scrolling, no stale duplicate help after modal close/field mode switch |
| Regression | Tool finder points to actual controls, undo/redo, numeric/reset, 7-builder state/reload, project versions and backups, mounting hole positions, prepared manufacturing/print jobs remain intact |
| Release | Product implementation PR updates in-app Help, What’s New, external user guide, CHANGELOG/version and Pages-specific app guidance **only once implementation passes**; exact-head static/browser/manufacturing gates |

Use existing `npm run test:static`, `npm run test:browser` and `npm test`, plus focused new `tests/context-help*.test.mjs` modules; do not change CI workflow classifiers merely to run docs. Follow `docs/TESTING.md` and issue #10 physical limitations. Reports must distinguish unit/static from real Chromium, automated geometry from actual prints, and CI exact head from earlier merged runs.

## Implementation sequence and boundaries

1. **Docs/contract PR (this planning lane):** issue, audit, blueprint, agent fast start, *future* user guide text; no working UI or release claims. It may merge without shipping a feature, subject to owner approval.
2. **Core UX PR:** tiny stable help preference/renderer/registry layer; fix tooltip hoverability, identity, keyboard/touch/contrast. Cover an end-to-end Crystal and native control with tests; retain legacy behaviour until replacement tested.
3. **Comprehensive parity PR:** fill all controls, seven families and eight workspaces, including dynamic editors, editorial audit and coverage gate. Prefer smaller independent content batches if a single giant diff impedes review; use **one canonical registry**.
4. **Ship step:** remove old descriptions sidebar and old button only when parity proved; update in-app Help/What's New and external guides, release metadata and Changelog in the final UI PR, not in this planning PR. Pages deploys automatically when main changes; never manually publish a plan as a completed feature.

**Current ownership:** WT-023 #147, #148, #151 implement project/library/vault. QA #149 edits `AGENTS.md` and the current status/map; #150 owns regression tests. Do not modify those branches, overwrite their files or start a crosscutting Studio refactor. Implementation should branch fresh main **after checking owners, CI and changed paths**, or explicitly stack with a documented dependency. The planning branch intentionally avoids `AGENTS.md` / `docs/PROJECT_STATUS.md` to reduce conflicts.
