## Source audit and design
- Classic: index.html #colours is a fixed set of buttons with data-colour numeric hex strings. studio-v3.js syncForm matches Number(dataset.colour) to s.colour; existing click handler assigns Number, syncForm, rebuild, snapshot. Saved source uses numeric parameters.colour. updateAppearance manages lighting/selection/wireframe, not a replacement material picker. crystalStartingPointPreview in studio-crystal-presets.js reads settings.colour using nullish fallback; preserve zero and legacy saved values.
- Native: sensory-studio.js showGeneric, refreshChamferPreview and renderSavedPreview feed primary/secondary material colour into previewRecipe. These paths use logical OR defaults and therefore reject black (numeric zero). Replace all relevant colour reads with one validated/nullish default resolver, including prepared mesh appearance if applicable. studio-geometry.js previewRecipe already assigns colour by actual primary/secondary region. Native renderEditor/Design choices does not provide a universal arbitrary colour control. Existing commit() calls editModel, rebuild and save; native history snapshots currently capture only parameters/build, not materials. Add material state to history and ensure every producer of history snapshots is compatible, rather than pretending a colour change can already undo.
- studio-documents.js modelFingerprint includes materials and parameters, editModel increments revision and marks affected prepared jobs stale for every edit. Keep existing revision safety initially; do not introduce a hidden appearance-only bypass that can attach stale manufactured output to new revision. Compare geometry independently of colour, and preserve material region identities. If a future optimization is desired, propose separate reviewed geometry-vs-appearance fingerprint contract.
- Saved preview cache includes source fingerprint, model ID, project ID and revision. Reuse this to show newly chosen colours in drawer and Library; don't tint old PNGs. Imported source supports only its declared material capabilities. Existing two-region split geometry, simulated LED glow, theme colours, selection, warnings and heatmaps are separate semantics.
- Project scope: arbitrary colours are model data, not global view preferences. Project palettes/reusable material records can be a later #141 resource extension; avoid adding an unapproved global catalogue or changing the workspace schema in this slice.

## Interaction
Design → Model appearance (shared location for every builder) with labelled Primary model colour, Secondary model colour only where supported/active, 16–24 curated quick swatches with readable names, a native colour picker and explicit #RRGGBB text field. Display current value and a selected state independent of colour. Example swatches: white, grey, black, red, orange, yellow, lime, green, teal, cyan, blue, indigo, purple, magenta, pink, brown. Users can choose any 24-bit sRGB value, not just these swatches. Use native input type=color plus text fallback because browser picker UI varies; validate six hex digits, allow optional leading # on explicit text commit, normalize uppercase. Reject malformed/alpha/wide-gamut input with explanation rather than silently selecting black. Persist integer 0..0xFFFFFF in the existing field; format using padded six-digit hex. Use existing Crystal undo/capture mechanism and native commit/history; disabled linked copy until independent variant. Preserve a previously selected secondary when toggling dual-material off/on. Use explicit Apply/Cancel if needed to avoid dozens of revision/geometry rebuilds during dragging; one committed choice = one undo entry. Do not change source when opening or cancelling picker. Keep LED glow separate and label the difference; no claim this matches filament appearance or printed colour.
